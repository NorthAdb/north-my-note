## 一句话总结

> Agent 的上下文管理不是简单删除旧消息，而是同时维护**原始会话链、模型接口视图和用户界面历史**，通过上下文投影、压缩摘要、Prompt Cache 和会话恢复机制，让长任务在有限上下文窗口中持续运行。

## 一、为什么上下文会溢出

长时间运行的 Agent 会不断累积：

- 用户消息和模型回复
- 工具调用参数与工具结果
- 文件内容、日志、搜索结果和代码片段
- 规划、状态、错误和重试信息

真正占用上下文窗口的，往往不是普通对话，而是**工具结果和长文本**。如果把所有历史原样发送给模型，最终会超过模型上下文窗口，导致成本、延迟和失败率上升。

## 二、三个版本的“历史”

视频强调，成熟 Agent 中至少存在三个不同视图：

| 视图 | 作用 | 是否是事实源 |
|---|---|---|
| 用户界面历史 | 让用户看到完整、连续的交互过程 | 展示层 |
| 模型接口视图 | 当前这一轮真正发送给 LLM 的消息 | 投影结果 |
| 磁盘逻辑会话链 | 持久化消息、工具调用、状态和恢复信息 | 更接近事实源 |

三者不必完全相同：用户界面可以保留完整历史，模型接口只携带压缩后的有效上下文，磁盘则保留可重建的逻辑会话链。

## 三、上下文投影：不直接修改原始历史

### 核心思想

不要把原始会话记录直接改短，而是从持久化历史中生成一个适合当前模型调用的“投影”：

```text
持久化的完整会话链
        ↓
选择边界、压缩旧消息、折叠工具结果
        ↓
当前模型接口视图
        ↓
发送给 LLM
```

这样做的好处是：

- 原始历史仍然可审计
- 可以重新生成不同版本的上下文
- 压缩策略变化后可以重新投影
- Resume 时能从原始记录恢复，而不是依赖一次压缩结果
- 用户界面仍可以展示较完整的交互历史

### 为什么不要原地删除

如果直接删除磁盘中的旧消息，会带来几个问题：

- 无法审计 Agent 之前做过什么
- 无法重新解释工具调用和决策依据
- 恢复会话时缺少必要状态
- 压缩策略出错后无法回滚

更稳妥的方式是：**保留原始链，另外生成摘要、边界和投影视图**。

## 四、上下文压缩不是简单删除

当上下文接近上限时，系统可以：

1. 找到合适的压缩边界。
2. 识别旧消息中的任务目标、关键决策、未完成事项和重要结果。
3. 把冗长的工具输出和旧对话折叠为结构化摘要。
4. 保留原始历史记录。
5. 用摘要占位符代表已折叠的历史。
6. 从新的逻辑起点继续追加消息。

```text
原始历史：m1 → m2 → m3 → ... → m80

模型投影：
摘要(m1...m50) → m51 → m52 → ... → 当前消息
```

关键区别是：**压缩的是模型视图，不一定是事实源本身**。

## 五、Prompt Cache 对上下文设计的影响

上下文压缩不能只考虑 token 数量，还要考虑缓存命中。

如果每轮都重写系统提示词和历史前缀，即使消息变短，也可能破坏 Prompt Cache，导致：

- 缓存命中率下降
- 输入成本上升
- 首 token 延迟增加
- 长任务运行效率变差

因此，缓存友好的设计倾向于：

- 保持稳定的系统提示词
- 尽量保持历史前缀稳定
- 只在末尾追加新的事件和结果
- 在明确边界处做压缩，而不是每轮随意改写全部历史

可以把它理解为：**上下文管理同时优化“能装下多少”和“有多少内容可以复用”。**

## 六、会话恢复为什么不只是读取聊天记录

Resume 不等于把 UI 中的消息重新显示出来。真正的恢复还需要重建：

- 当前 Agent 处于哪个任务阶段
- 哪些工具已经调用过
- 工具返回了什么结果
- 哪些步骤已经完成
- 哪些任务仍未完成
- 当前工作目录和文件状态
- 运行时配置、权限和模型上下文
- 下一步应该从哪里继续

因此，会话恢复更像是：

```text
读取逻辑会话链
    ↓
重建状态和上下文投影
    ↓
恢复工具、工作目录和任务边界
    ↓
继续 Agent Loop
```

## 七、Resume 与 Fork 的区别

| 操作 | 含义 | 典型用途 |
|---|---|---|
| Resume | 在原会话上继续执行 | 网络中断、上下文压缩后继续任务 |
| Fork | 从某个历史点复制出一条新分支 | 尝试另一种方案，不影响原任务链 |

这说明会话系统不只是“聊天记录列表”，而是一个可以恢复、分支和投影的状态图。

## 八、完整的长任务生命周期

```text
1. 用户提出任务
2. Agent 调用模型和工具
3. 持久化消息、工具结果和运行状态
4. 生成模型当前视图
5. 接近上下文上限时触发压缩
6. 生成摘要并记录压缩边界
7. 保留原始逻辑链
8. 从新边界继续 Agent Loop
9. 中断后 Resume，重新投影上下文
10. 必要时从历史点 Fork 新分支
```

## 九、对 Agent 系统设计的启示

### 1. 把事实源和展示视图分开

不要让“发送给模型的消息”成为唯一数据源。建议分别保存：

- 原始事件日志
- 当前会话状态
- 模型上下文投影
- 用户界面展示历史

### 2. 压缩要有边界和证据

压缩后至少应该保留：

- 原任务目标
- 已完成步骤
- 未完成事项
- 关键工具结果
- 重要决策和原因
- 当前工作目录或资源状态
- 下一步建议

### 3. Checkpoint 是恢复的基础

长任务不能只依赖上下文窗口。每个阶段应保存可恢复的 checkpoint，尤其是：

- 工具调用前后
- 文件修改后
- 子 Agent 返回后
- 人工审批前后
- 上下文压缩完成后

### 4. Prompt Cache 是架构约束

上下文结构需要从一开始就考虑前缀稳定性。Prompt Cache 不是单纯的 API 优化，而会反过来影响：

- 消息排列
- 压缩时机
- 系统提示词组织
- 工具定义注入方式
- 多轮 Agent 的成本和延迟

## 十、与 Harness / Loop / Graph 的关系

这期视频主要讲的是 **Harness 内部的上下文与会话层**：

| 层 | 与本视频的关系 |
|---|---|
| Harness | 提供上下文、工具、Memory、持久化和恢复能力 |
| Loop | 决定压缩、重试、状态更新和何时继续执行 |
| Graph | 将压缩、Checkpoint、人工审批和子 Agent 编排成可控流程 |

可以把上下文压缩和会话恢复看成 Agent Harness 的“状态基础设施”，不是单独的提示词技巧。

## 十二、AI 字幕补充的实现细节

完整 AI 字幕进一步把上下文处理拆成了几类机制。它们的共同点是：**主要修改发给模型的接口视图，不直接改写磁盘上的原始事件记录**。

### 1. 工具结果外置

当工具返回五万行日志或大文件时，不把完整结果继续塞进上下文，而是：

```text
完整工具结果 → 写入磁盘
             → 接口视图只保留预览片段 + 文件位置
             → 模型需要细节时再次读取
```

这不是语义摘要，原文仍然保留，适合处理超大工具结果。

### 2. 微压缩 / Snip

对已经确认无用的中间尝试和旧工具结果，从接口视图中移除；同时在磁盘中追加一份精确的删除清单。恢复时重新执行这份清单，就能得到相同的模型视图。

### 3. 上下文折叠

把一段旧消息折叠成一个摘要占位符：

```text
多轮排查日志 → 一条摘要占位符
```

交互历史和磁盘原始消息保持不变，磁盘只追加一条“如何投影”的说明；恢复时按这条说明重新生成接口视图。

### 4. 全量压缩

当上下文接近窗口上限，或用户手动触发压缩时，把压缩边界之前的完整历史总结成摘要，并在逻辑链上建立新的起点。之后的请求从新边界继续，不再自动携带边界之前的历史。

全量压缩是少数会改变“当前逻辑链起点”的机制，但并不等于删除磁盘上的旧记录。

### 5. 响应式压缩

客户端估算 Token 可能不准确，真实请求仍可能被服务端拒绝。此时才启动响应式压缩：

1. 总结历史并建立新的逻辑链。
2. 用新历史重试一次。
3. 如果恢复仍失败，直接暴露原始错误。

它只允许尝试一次，避免恢复逻辑自身不断扩大上下文并进入死循环。

### 6. 缓存热度决定压缩方式

字幕还提到两种与缓存状态相关的路径：

- 缓存已冷却：前缀本来就要重建，可以直接把旧结果替换为占位摘要。
- 缓存仍然热：尽量不改本地前缀，改用接口层的缓存编辑，让服务器端移除旧结果，从而保住 Prompt Cache。

这解释了为什么系统有时宁愿多消耗一些 Token，也不愿修改已经发送过的前缀字符。

## 十三、追加日志与父指针图

视频字幕把磁盘记录描述为一个**只追加的事件文件**，但逻辑上不是简单数组，而是一张带父指针的消息图：

- 每条消息记录自己的上一条逻辑消息。
- 并行工具结果可以从同一条助手消息分支出去。
- Resume 时先找到当前活动分支的末端，再沿父指针回溯重建逻辑链。
- 全量压缩写入的新边界相当于一个新的逻辑起点。
- Fork 会创建新的会话 ID 和分支，不接管原会话的记录文件和工作树所有权。

因此，Resume 不是把 JSON 文件重新读入内存，而是：

```text
重建活动消息链
  → 重放外置预览、Snip、折叠等投影记录
  → 修复未完成的工具调用/结果结构
  → 恢复文件、Skills、Agent、工作目录等运行时状态
  → 继续安全执行
```

字幕特别强调，恢复时还要处理中断留下的半成品：工具调用和结果重新配对、消息角色保持合法、必要时补充继续执行的消息。

## 十四、适合你的学习顺序

结合 Java 后端 + Agent 学习路线，建议按以下顺序实现一个简化版：

1. 用数据库保存不可变的消息和工具事件。
2. 增加 `session_state`，保存任务阶段和未完成事项。
3. 实现一个简单的上下文窗口估算器。
4. 超过阈值时，将旧消息压缩成结构化摘要。
5. 保留原始消息，只改变发送给模型的投影。
6. 增加 checkpoint 和 resume。
7. 最后再加入 Prompt Cache、Fork、子 Agent 和 Graph 编排。

一个最小数据模型可以是：

```text
Session
 ├── EventLog          # 不可变事件链
 ├── SessionState      # 当前任务状态
 ├── ContextProjection # 当前发送给模型的视图
 ├── Checkpoint        # 可恢复边界
 └── Branches          # Fork 出来的会话分支
```

## 结论

成熟 Agent 的上下文管理，本质是一个**事件持久化 + 状态管理 + 视图投影 + 压缩 + 可恢复执行**系统。

> 真正的上下文工程不是“把旧消息删掉”，而是保留可追溯的事实源，再为模型生成足够小、足够新、可缓存、可恢复的上下文视图。
