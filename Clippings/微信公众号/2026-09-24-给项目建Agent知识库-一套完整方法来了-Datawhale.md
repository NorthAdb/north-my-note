# 给项目建 Agent 知识库，一套完整方法来了

> **来源**：公众号「Datawhale」，作者王大鹏，2026-09-24。
>
> **一句话总结**：给项目建 Agent 知识库，难点**不在"资料从哪里找"，而在"查到资料以后凭什么判断"**。所以要反过来做——**先确定知识库要支持什么判断，再决定整理什么、整理到什么程度**，最后用"下一次问题里的表现"来验收，而不是用文档数量来验收。

## 0. 立论：知识库的失败模式不是"查不到"，而是"查到了也不会判断"

常规做法：一个项目通常能拿到**架构文档、接口说明、历史复盘**，代码也在仓库里。于是很容易想到——把资料整理好、做索引，让 Agent 遇到问题去查。

这解决了 **"资料从哪里找"**。但如果目标是**让 Agent 定位生产故障**，还要多问一句：

> 查到资料以后，它**凭什么判断**这次问题发生在哪里？

### 反例：HTTP 500 不等于"删除失败"

| 环节 | 现象 | 结论 |
| --- | --- | --- |
| 接口返回 | `DELETE` 返回 **HTTP 500** | Agent 据此判断"删除失败" |
| 查数据 | 数据**已经删除** | 服务端处理请求时出错，**不代表之前执行的动作没有生效** |
| 后果 | 只凭状态码决定**重试**或**把结果改回去** | 两种处理**都可能是错的** |

接口说明没缺、错误码解释也没缺——**要判断这次故障，还得知道**：

1. 删除过程**经过哪些环节**；
2. 错误发生前**哪些步骤已经完成**；
3. **从哪里能查到实际结果**。

这就是本文的核心：**缺的不是资料，是"判断所需的结构"。**

## 1. 先确定需要支持什么判断

建设知识库之前，先确定它要帮 Agent 做什么。**这里的目标是"定位生产问题，并为是否修改、修改哪里提供依据"——这个目标决定了资料要整理到什么程度。**

| 要素 | 说明 |
| --- | --- |
| **预期** | 判断一个行为有没有问题，需要一个**预期**作参照：接口原本要完成什么、允许哪些中间状态、出现错误后**保证到哪一步**。否则"当前状态是什么"只是一条记录，**不足以判断它是否异常** |
| **实现机制** | 有了预期，还要知道**系统靠什么实现它**。同一个结果可能经过多个服务和后台任务，用户看到的错误可能出现在后面的环节，**原因却在前面**。只列组件名称无法解释这种关系，需要把过程连起来：每一步的**输入、结果、失败后会发生什么** |

### 判断所需的信息 = 一个固定的"槽位"结构

> **哪个机制原本应该完成什么；实际行为在哪个环节偏离了预期；有什么证据，造成了什么影响。**

这里的**"机制"**，就是系统完成一件事所依靠的过程——它可能在一个服务内完成，也可能跨越多个组件。

这句话**还没涉及当前项目的具体实现**，却已经给出了整理资料的方向：

| 资料类型 | 应该能回答 |
| --- | --- |
| 架构文档 | 这段过程**涉及谁** |
| 设计文档 | **正常行为**是什么 |
| 代码与观测资料 | 帮助确认**实际执行到了哪里** |

![解决未知问题，先把问题放进结构里：机制与承诺 → 流程环节 → 事实核对 → 影响与处理](https://gitee.com/cheng-jiaqing/images/raw/master/cordis/agent-kb-fig1-problem-structure.png)

图中的槽位（**不是固定排查步骤，而是做出判断时需要补齐的信息**）：

| 槽位 | 要回答的问题 |
| --- | --- |
| **机制** | 谁负责这件事 |
| **承诺** | 本来应该怎样 |
| **环节** | 偏离发生在哪一步 |
| **证据** | 事实能证明什么 |
| **影响** | 功能、资源、其他调用 |
| **处理** | 修改、避开还是观察 |

> **关键用法**：刚拿到故障时，**可以只知道现象，其余位置暂时留空**；后续调查的任务就是**逐步缩小这些未知**。

## 2. 不熟悉项目，先整理"它正常时怎么工作"

有了上面的结构，仍然**不能凭空知道**某个模块有哪些状态，也不能推导出线上用了什么配置。

> **第一性原理能帮助确定"需要了解什么"，项目事实还得去查。**

做法上有一条明确的取径：**从一条完整的业务流程开始，而不是试图一次读懂整个仓库。**

1. 先用**文档**确定这条流程的**目的和边界**；
2. 再沿**代码**核对它**实际经过的环节**；
3. **调用顺序、状态变化和失败处理放在一起看**，才能得到一份"正常工作过程"的说明；
4. **函数所在的文件可以作为查证入口，但文档的主体应当是过程本身。**

### 整理纪律：宁可留空，不要猜

- 不熟悉的地方要**留下问题**，而不是猜一个解释让文章读起来完整；
- 文档和实现对不上，就**记录冲突**；
- 代码看不出设计原因，就找**设计记录**或请**维护者确认**；
- **暂时没有答案，并不妨碍先整理已经核实的部分。**

逐条补充关键流程以后，系统的整体结构也会清楚起来：**哪些过程共享同一项状态、哪些失败会传到其他环节、哪些结果可以重试、哪些动作一旦完成就不能简单撤销**——这些关系是定位新问题时会反复用到的知识。

### 自检：整理是否足够？

> 假设某个环节没有按预期工作，**Agent 能否从文档中找到"正常行为"和"查证位置"**？
>
> 如果只能找到一段**职责介绍**，还要重新读完整个模块才能理解流程——**这部分知识就没有整理到位**。

> **专家认知 = 问题结构 × 对应的领域知识**
>
> 这个公式是一种**设计上的简写，不是数学计算**。问题结构帮助确定"要回答什么"，领域知识提供"具体内容"。**只写一组问题、没有对应内容，Agent 依然需要从头了解项目。**

## 3. 把"文档这样写"变成"有依据的判断"

沿流程整理之后，通常会遇到一个问题：**同一件事，不同资料说法不同。**

| 资料 | 反映的是 |
| --- | --- |
| 设计文档 | **当初希望**怎样实现 |
| 代码 | **某个版本**实际怎样实现 |
| 线上运行 | **未必是仓库最新版本** |

**不能简单规定"永远以代码为准"**，然后把所有冲突都解决掉。需要**先明确正在确认什么**：

| 问题 | 要核对的东西 |
| --- | --- |
| 当前**生产行为**是什么 | 部署版本、实际配置、运行记录 |
| 系统**应该遵守的接口约定**是什么 | 对应版本的**契约**（实现违反了契约，也可能正是待修的问题） |

> **每条重要结论都要保留依据、适用条件和待确认事项。** 整理者相信它，**不足以**让另一个 Agent 直接拿去使用。

> **专家知识 = 专家认知 × 事实验证**

专家知识可以**保留稳定的判断依据，把容易变化的值留在事实来源里**：

- 代码入口、接口字段、日志字段**并非一律不能写**——它们如果有助于查证，**就应保留在参考资料中，并注明适用范围**；
- 需要避免的是**把某次查到的值写成长期不变的规律**。

这些内容整理到一起，才不只是对资料的概括：**后来接手的人能沿着依据核验结论，也能知道哪些地方不能直接套用。**

## 4. 让 Agent 找得到，也知道怎样使用

经过核验的知识仍然可能**分散在很多文件里**。Agent 每次都从全库搜索开始，**容易先命中旧复盘或零散细节，而没有读到当前机制的完整说明**。

解法：在这些资料前面放一份**较短的入口文档**——它说明系统的关键过程，列出正常行为和重要约束，再**指向详细资料与查证位置**。这份优先读取的文档，就是**专家底座**。

| 概念 | 指什么 |
| --- | --- |
| **专家知识** | **内容**本身 |
| **专家底座** | **组织和提供这些内容的方式** |

底座的要求：

- **不需要装下全部资料，但也不能只剩一张目录**；
- **Agent 读完以后，至少应当理解"当前问题所在模块正常时怎样工作"。**

### 使用姿势：知识库提供"参照系"，不提供"答案"

- Agent 先把**现象**放到对应**流程**中；
- 知识库提供的是**正常过程和已知约束**，**现场调查**确认的是**这一次发生了什么**；
- 两者不一致时，**需要继续取证**，**不能为了让事实符合文档而忽略差异**。

### 「求证方法」要单独准备

哪些信息只是**线索**、怎样检查一个解释是否有**反例**、什么情况下**仍不能动手修改**——这些**不属于某个模块的工作原理**。

> **懂得正常流程，并不保证每次推断都正确。**

> **未知问题的解题能力 = 专家知识 × 求证方法 × 当前事实**

### 用开头的删除案例验收

> Agent 能否**把"返回错误"和"动作结果"分开**、**找到检查实际结果的位置**，而不是**看到错误码就直接处理**？
>
> 如果**必须由使用者反复提醒**，说明**知识或使用说明还需要补充**。

> **注意**：专家底座提供**认知参照**，**不规定每次都执行同一组命令**。成熟的操作手册仍然有用，但**只能在它的适用条件已经得到确认时使用**。

## 5. 知识要分开保存，才能按不同速度更新

整理专家知识，并不意味着其余项目资料都没用了。**完整的实现说明、接口定义和操作记录仍然需要保存，只是不能把它们当作同一种知识使用。**

| # | 分类 | 内容 | 变化速度 / 来源 |
| --- | --- | --- | --- |
| 1 | **领域知识** | **在不同项目中也能使用**的概念和机制 | 适用条件通常比较稳定，但**应用到当前项目时仍需核对** |
| 2 | **项目设计与实现记录** | 这个系统**自己的**组成、流程和约束 | 不一定能迁移，但**定位当前项目问题必不可少** |
| 3 | **接口文档** | **精确契约** | 字段和错误语义需要**跟版本一起维护** |
| 4 | **使用与运维资料** | 操作方法、适用条件、**回滚步骤**；排期与责任分工也归这类 | **不能当成长期规则** |
| 5 | **日期目录和草稿区** | 分析过程、**尚未确认的猜测** | 可以保留猜测，但**不应和已核实的结论混在一起** |

> **分类的判据**：看一条内容的**用途、变化速度，以及由什么来源来确认**。
>
> **不同分类是维护方式的区别，并不是价值高低的排序。** 专家知识也可能来自对项目实现的深入理解，**不只来自通用原理**。

### 防重复：结论只存一份

一份故障复盘**不必整篇搬到某个目录**。正确做法是：

- **过程记录留在原处**；
- **已经确认的结论分别更新到对应资料**（领域知识 / 项目知识 / 契约 / 运维）；
- **再由索引建立联系**。

> 否则同一个结论在几份文档里各存一遍，**后面很难保证同时更新**。

## 6. 用新问题检查旧知识

知识库是否有用，**要看它在下一次问题中起了什么作用**。

### 排查结束后的归因表（不要一律归为"知识不够"）

| 走偏的方式 | 该检查什么 |
| --- | --- |
| **找错了模块** | 入口是否清楚 |
| **正常流程理解错了** | 核对相关文档 |
| **知道流程却得出了没有证据的结论** | 检查**求证要求** |

> 把这些问题**一律归为"知识不够"**，很容易又回到**增加文档数量**的做法。

### 更新粒度与回归

- 更新**不必每次重写整份底座**：局部理解有误就修正相关内容；**出现原有结构容纳不了的问题，再调整结构**；
- 改完后**重跑之前的案例**，确认旧问题仍能被正确分析；
- **检查数量可以少，但最好有未参与编写的人或 Agent 独立完成**，避免**照着已知答案验收**。

### 定期复核

| 触发 | 动作 |
| --- | --- |
| 依赖版本、关键配置、接口变更 | 检查**关联结论** |
| 日常整理 | 处理**未确认项**和**日期目录中的新发现** |
| 每条正式结论 | 留下**来源**与**最近核验时间**，后续维护者才知道该从哪里查起 |

> **没有新证据的猜测，不因重复出现就升级为事实。**

### 收尾心态

刚接手一个陌生项目时，**不可能一次写出完整的专家知识**。能够做到的是：

- 让**每个判断有出处**；
- 让**不知道的地方清楚可见**；
- 新问题来了，**沿着已有过程继续核对**；
- 处理完以后，**下一位使用者少走一段相同的弯路**。

## 7. 四个公式速查

| 公式 | 含义 | 用途 |
| --- | --- | --- |
| **专家认知 = 问题结构 × 对应的领域知识** | 问题结构定"回答什么"，领域知识给"具体内容" | 决定整理方向 |
| **专家知识 = 专家认知 × 事实验证** | 稳定判据留着，易变值回到事实来源 | 决定写什么、不写什么 |
| **未知问题的解题能力 = 专家知识 × 求证方法 × 当前事实** | 知识、方法、现场事实缺一不可 | 决定验收标准 |
| **专家底座 = 组织与提供这些内容的方式** | 短入口文档 + 指向详细资料与查证位置 | 决定 Agent 第一眼读什么 |

## 8. 复习版结论

1. **先问"要支持什么判断"，再问"整理什么资料"**——目标决定整理程度。
2. **判断需要一个预期作参照**：机制原本应该完成什么、错误后保证到哪一步。
3. **从一个已知现象出发，但不要从现象直接跳到结论**（HTTP 500 只是响应结果，不是执行结果）。
4. **不熟悉项目，就先整理"它正常时怎么工作"**——从一条完整业务流程开始，而不是读懂整个仓库。
5. **留白优于猜测**：冲突、疑问、待确认项都要显式记录在案。
6. **没有"永远以代码为准"**：先明确在确认"生产行为"还是"接口契约"。
7. **重要结论必须带来源、适用条件、待确认项和核验时间。**
8. **入口文档（专家底座）不能只剩目录**：读完至少要懂"当前模块正常时怎么工作"。
9. **求证方法独立成篇**：懂流程 ≠ 推断正确。
10. **知识按更新速度分层保存**，同一结论只存一份，由索引建立联系。
11. **验收看"下一次问题里的表现"**，并按"走偏在哪里"分类归因，而不是无脑加文档。

## 9. 对我们的启示 & 生产落地

> 这一节是自己的延伸，不是原文内容。

### 9.1 六条最值得抄走的认知

| # | 启示 | 为什么反直觉 |
| --- | --- | --- |
| 1 | **知识库的价值不在"覆盖"，在"能判断"** | 我们默认"文档越多越好"；本文说**资料整理的程度由判断目标决定**，多余资料反而制造搜索噪声 |
| 2 | **"响应结果 ≠ 执行结果"** 是故障定位的第一课 | 大多数 Agent（和很多人）看到 5xx 就重试/回滚；分布式系统里"请求失败"和"动作未生效"是两件事 |
| 3 | **需要的是"槽位"，不是"清单"** | 排查清单是固定步骤，槽位是**判断缺什么就补什么**；前者僵化，后者可迁移 |
| 4 | **第一性原理只解决"该了解什么"，不解决"事实是什么"** | 很多人以为想清楚就够，本文强调**项目事实必须去查**，且**查不到就留空** |
| 5 | **没有"永远以代码为准"** | 设计文档=当初希望、代码=某版本实现、线上=未必同版本；**先问"我在确认什么"** |
| 6 | **失败归因要分类，而不是归为"知识不够"** | "知识不够"是退化成"堆文档"的入口；应按**入口问题 / 流程理解问题 / 求证问题**分别修 |

### 9.3 生产落地：一份可直接照做的施工单

#### 第 0 步：写"要支持什么判断"，不写"要整理什么"

在动手前，先用一页纸写下这个问题模板（**这就是槽位**）：

```text
机制：<谁负责这件事>    承诺：<本来应该怎样>
环节：<偏离发生在哪一步>  证据：<事实能证明什么 / 去哪里查>
影响：<功能 / 资源 / 其他调用>   处理：<修改 / 避开 / 观察>
```

**判据**：如果这张单子写不出具体的"证据去哪查"，说明还没到能建库的程度。

#### 第 1 步：选一条真实业务流程，而不是整个仓库

对 Java 后端服务，取一条**写路径**最合适（删除、下单、支付回调），因为它**跨越的环节最多、最容易被 5xx 骗到**：

```text
Controller → 参数校验 → Service → 本地事务 → 缓存失效 → 发消息/事件
   → 下游 RPC → 异步任务 → 对账/补偿
```

每个环节都写四件事：**输入、输出、是否已产生副作用、失败后会发生什么**。
重点标出**不可撤销的动作**（已提交的事务、已发出的 MQ、已扣减的库存）——这是重试决策的关键。

> **自检**：随便挑一个环节，问 Agent「这一步正常时应该是什么样、去哪查它到底做没做」。答不上来就是没整理到位。

#### 第 2 步：写一份"专家底座"入口文档（最小版 1 页）

放哪都行，关键是**被优先读取**：仓库根目录的 `AGENTS.md` / `CLAUDE.md` 的一段、或 `docs/agent-index.md`，再在 CLAUDE.md 里指过去。

```markdown
## 系统关键过程（优先读）
- 写路径：<一条链路图>
- 幂等与重试：<哪些动作可重试、哪些绝对不行>
- 事务边界：<在哪提交、提交后出错怎么办>

## 重要约束
- <不变量 1：例如"状态机只能单向流转">

## 详细资料与查证位置
- 领域知识 → 领域/
- 项目实现 → 项目/xxx
- 接口契约 → <OpenAPI + 版本>
- 日志/追踪字段 → <表名 / traceId / 关键字段>
- 运维操作与回滚 → <runbook 链接>
```

**底线**：底座**不能只剩目录**——读完至少要懂"当前模块正常时怎么工作"。

#### 第 3 步：把"求证方法"单独写成一篇

这篇文章不属于任何模块，但决定 Agent **敢不敢动手**：

| 内容 | 例子 |
| --- | --- |
| 什么只是线索 | 5xx、告警、用户描述 |
| 怎么验证一条解释 | 查 DB 实际行、查 binlog/审计表、查 MQ 投递记录、查 traceId 全链路 |
| 什么时候**仍然不能**动手 | 副作用已发生、无法幂等、证据链断裂、影响面未知 |
| 怎么证伪 | 主动找**反例**：如果真是 A 导致的，那 B 现象应该也出现，但它没有 |

#### 第 4 步：按更新速度分层，并且只存一份

| 层 | 放什么 | 更新触发 |
| --- | --- | --- |
| 领域知识 | 幂等、事务、最终一致性、状态机等**跨项目**概念 | 很少变，但**用到当前项目时仍要核对** |
| 项目知识 | 本系统的组成、流程、约束 | 流程改动时 |
| 契约 | OpenAPI / 错误码语义 / 事件 schema | **跟版本一起维护** |
| 运维与排期 | 操作步骤、适用条件、回滚、责任人 | 每次都变，**不能当长期规则** |
| 过程草稿 | 每日分析、未确认猜测 | 随时，**与已核实结论隔离** |

> **正好和我们这个 vault 的结构同构**：`领域/` = 领域知识，`项目/` = 项目知识，`Clippings/` = 外部契约与参考，`日记/` = 过程草稿。
> 所以本文的方法不仅适用于代码仓库，**也可以用来解释/治理我们自己的笔记库**。

#### 第 5 步：建一个"故障判断回归用例集"

像写测试一样写 case（放在 `项目/xxx/evals/` 或运维文档里）：

```markdown
### CASE-001 删除接口 500，但数据已删除
- 期望 Agent 的行为：先分开"响应结果/执行结果"，去查实际行 + 审计记录
- 判定：❌ 看到 500 直接重试 / ✅ 取证后再决定
- 最近核验：2026-09-27
```

**规则**：
1. 每次排查结束，记录 **Agent 是从哪里开始走偏的**（入口？流程理解？求证？）；
2. 改完后**重跑旧 case**；
3. 验收**最好由没参与编写的人/Agent 独立完成**——否则就是照着答案验收；
4. 依赖版本、配置、接口变更后，**检查关联结论**并更新时间戳。

#### 第 6 步：给每条结论加上"可维护的前缀"

在笔记/文档的 frontmatter 或句尾带上：

```yaml
结论: 删除接口在事务提交后会同步失效缓存，失败需补偿
来源: <代码入口 / 设计记录 / 维护者确认>
适用版本: xxx@v1.4.x
最近核验: 2026-09-27
待确认: 异步任务失败时是否自动重投
```

> 这条纪律的收益很直接：**换人接着维护时，他知道从哪查起；换 Agent 接手时，它知道哪些能直接套用、哪些必须先取证。**

### 9.4 30 天最小可行路径（不追求一次写完）

| 阶段 | 做什么 | 完成标志 |
| --- | --- | --- |
| 第 1 周 | 写问题模板 + 选一条写路径，沿代码核对流程 | 产出"正常工作说明"，含不可撤销动作清单 |
| 第 2 周 | 写 1 页专家底座入口文档，挂到 `AGENTS.md`/`CLAUDE.md` 的优先读位置 | Agent 新会话第一眼就读到它，并能说出"这模块正常怎么走" |
| 第 3 周 | 写求证方法一篇 + 6 个真实故障 case（含 1 个"5xx 但动作已生效"） | case 能被独立运行、独立判定 |
| 第 4 周 | 按更新速度分层归位，打来源/版本/核验时间戳，处理未确认项 | 没有同一结论的两份副本；每份正式结论都能溯源 |

### 9.5 反面清单（要避免的四个坑）

| 坑 | 表现 | 后果 |
| --- | --- | --- |
| **把整理当覆盖** | 只问"资料齐了吗" | 文档很多，Agent 仍不会判断 |
| **把猜测写进正文** | 为了让文档读起来完整而补一个解释 | 猜测被后续读者当事实，污染判断 |
| **同一结论多处存副本** | 复盘、设计文档、底座各写一份 | 无法保证同时更新 |
| **用"知识不够"解释所有失败** | 每次走偏就加文档 | 回到堆量的老路，边际收益递减 |

> **最终**：建 Agent 知识库不是"把项目资料喂给模型"，而是**把专家判断问题的方式显式化成结构**——**问题结构 × 领域知识 × 事实验证 × 求证方法**，再用**下一次问题**来验收。
> 它和 RAG 的分工也很清楚：**RAG 负责"找得到"，专家底座负责"第一眼看对"，求证方法负责"敢不敢下判断"**。
