# 重磅！从 Agent 开发到 Agent 算法，进阶指南来了

> **来源**：公众号「Datawhale」，作者郭子扬（东南大学研究生），2026-09-21。原文为个人观点分享，文中明确说明"后面慢慢展开"的部分尚未展开。
>
> **一句话总结**：**开发是把一个 Agent 从 0 快速做到 60，算法是做到 80 并不断追高**；而从 60 到 80 靠的不是"自己视角下的过程指标"，是一套 **Benchmark → 策略 → 上线** 的闭环——**用离线评测近似线上的先验，用上线后的真实后验反过来修正先验**。整篇文章其实是这条闭环上的一次"逐级 scaling"：评测侧 Rubric → Human Judge → LLM Judge → Reward Model，策略侧 Prompt → SFT → RL。

---

## 0. 立论：开发 vs 算法，差在"谁来判断好"

作者开头点出的争议问题：**Agent 开发和 Agent 算法到底有什么区别？**（也是很多人找工作关心的点）

他的判断：

> 把一个 Agent 从 **0 快速做到 60** 是**开发**；做到 **80 并不断追高** 就是**算法**。

关键分歧不在技术栈，而在**评价权归谁**：

| 阶段 | 主要动作 | 效果由谁判定 |
| --- | --- | --- |
| 0 → 60（开发） | 用 Prompt / Context / Workflow 把闭环跑通 | **自己视角下的过程指标**（"我觉得这次答得不错"） |
| 60 → 80+（算法） | 对齐真实业务目标、持续追高 | **上线后的真实业务指标** |

但这里立刻出现一个现实约束：

- **上线验证周期长、成本高**，不可能每次迭代都等线上反馈；
- 所以必须构建**离线 Benchmark**，尽可能对齐线上效果，**用快速的离线评估来指导先验策略迭代**；
- 最后再上线获取**真实后验**，反过来**修正和补充新的先验策略**。

> **结论**：一套相对完整的 Agent 业务迭代方法论是 **Benchmark → 策略 → 上线**。
> 从一个 **make sense** 的方案，到真正 **work**，再到足够 **solid**，中间还有很多方法论。

### 先验 / 后验这对词是全文的骨架

| 概念 | 在这篇文章里的所指 | 承载物 |
| --- | --- | --- |
| **先验** | 我们当前相信"怎么做才有效"的那套知识 | Prompt / Workflow / Rubric / SFT 进去的参数 |
| **后验** | 上线后真实用户给出的结果 | Online Metric、线上 bad case |
| **闭环** | 后验 → 更新 Rubric / 数据 / Reward → 成为下一轮先验 | Benchmark 的持续迭代 |

## 1. Benchmark：很多算法实习生的第一份工作

作者给了一个很具体的实习场景：**审 ICLR 论文**。

### 1.1 为什么必须拆维度：主观标准没法一步评估

"这篇论文好不好"天然主观、模糊，只能专家评，**很难机器一步评估**。做法是拆成**写作、创新性、实验**等多个维度，再分别定义**什么情况下应该得高分、什么情况得低分**。

这个就叫 **Rubric**：

> 把模糊的业务目标，**翻译成能够被没那么专业的人、和 LLM、程序可以稳定执行的评价标准**。

作者在这里做了一个很漂亮的类比——**三件事本质相同，都是"把模糊目标翻译成可执行物"**：

| 谁在翻译 | 输入（模糊） | 输出（可执行） |
| --- | --- | --- |
| **Rubric** | 我要什么 | 可**评估**条件 |
| **Agent** | 我要什么 | 可**执行**步骤（plan / action） |
| **Codex / Claude Code** | 我要什么 | 可**执行代码** |

> 注意这个类比的落点：Rubric 之于评测，等于 Harness 之于执行。**它们是同一种"翻译工程"在两条链路上的实例。**

### 1.2 四级 scaling：Rubric → Human → LLM Judge → RM

这是全文最有价值的结构。**评测的自动化程度是逐级 scaling 上去的**，每一级解决上一级的瓶颈，同时引入新的风险：

| 级别 | 做法 | 解决了什么 | 新的瓶颈 / 风险 |
| --- | --- | --- | --- |
| **① Rubric** | 拆维度、定义高低分边界 | "什么样的结果算好"变得**可描述** | 描述不等于能稳定执行 |
| **② Human as a Judge** | 自己 / 业务专家按 Rubric 看几条 case，先做一批人标，看**人人一致率** | 验证 **Rubric 本身能不能被稳定执行** | 最可靠，但**慢、贵、不能 scaling** |
| **③ LLM as a Judge** | 以高质量人标为 ground truth，用**手工 PE / AutoPE** 调 Judge Prompt 与超参（温度、top k、top p） | 把人工判断**自动化** | 每次评测都要跑一次大模型，**规模一大成本/时延不可接受** |
| **④ Reward Model as a Judge** | 把已验证的评价标准**蒸馏成低延迟、高吞吐的 RM** | 把自动化判断**规模化** | **Reward Hacking**，RM 不能当成永远正确 |

#### ① → ②：发现问题常常不在 Judge，而在 Rubric

先由自己或业务专家按 Rubric 看几条 case，验证 Rubric 本身到底能不能被稳定执行，通常会先找一批样本做人标、看**人人一致率**。

> **如果同一个 case，两个人按同一套 Rubric 仍然经常得出不同结论，那很多时候不是 Judge 不行，而是 Rubric 本身还不够清楚**——需要继续拆标准、补边界 case。

（"发现人可以标"之后，才谈得上研究怎么让 LLM 来标。）

#### ② → ③：LLM Judge 的验收标准是"复现人工"

目标是让 LLM **尽可能复现已经稳定下来的人工判断**：

1. 用高质量人标数据作为 **ground truth**；
2. 通过**手工 PE / AutoPE** 反复调整 Judge Prompt，以及温度、top k、top p 等超参；
3. 人-机一致率高 → **离线 Benchmark 初步可用** → 再去看线上的真实业务指标。

这里接上了第 0 节的闭环，也是全文最容易被忽略的一句：

> 如果发现**离线涨了、线上没涨**，那问题不一定在策略，**也可能说明 Benchmark 本身没有对齐真实业务目标**——需要继续根据**线上 bad case 和后验数据**去更新 **Cases、Rubric 和 Judge**。

所以：**Benchmark 不是一次性做完的，而是跟着业务一起迭代**（作者补充：LLM 泛化性很强，"一起迭代问题不大"）。

#### ③ → ④：LLM Judge 解决了自动化，没解决规模化

为什么已经能复现人工判断了，还要训 RM？

> 因为 **LLM Judge 解决了自动化评测，但没有解决规模化评测**。

- 当 **Benchmark、实验、RL rollout** 规模继续扩大时，每次都调用一个大模型做 Judge，**成本和时延会随评测量线性增长**（原文提示：对成本没概念可以看看 MiMo 的直播 RL）；
- 而且这个开销**很难通过缩减 prompt 长度来优化**；
- 所以把**已经验证过的评价标准蒸馏成一个低延迟、高吞吐的 RM**。

**为什么可以用更小的基模？** 因为能力要求不同：

| | 需要的优势 | 因此可以 |
| --- | --- | --- |
| **LLM Judge** | 泛化能力强 | 用通用大模型 |
| **Reward Model** | 只需在**业务对应的数据分布**里更强 | 用更小的基模 + 前面已有的评测数据来训 |

**RM 不是终点。** 因为有 **Reward Hacking**，RM 不能被当成永远正确，仍需**定期用人工 / LLM Judge 检测新的 bad case → 补充数据 → 重新训练和校准 RM**。

### 1.3 一句话记住这一章

> **Rubric 定义什么叫好，Human 积累人工判断的经验，LLM Judge 把人工判断自动化，Reward Model 再把自动化判断规模化。**

## 2. 策略：从跑通 Agent 到持续提升效果

作者对"做 Agent 策略"的定义很直白：

> 做 Agent 策略就是**做先验**，然后根据上线效果**把后验转化为先验**（数据驱动）。

而具体流程——**一定是从老实琢磨 Prompt 开始**。

### 2.1 Prompt 策略：先用 token 换精准度，把上限摸出来

来自作者的实务经验（与多位"优秀的小同行"讨论）：**大部分业务，按专家先验知识调好 Prompt 就可以先上一版**，再根据上线效果决定后续路线。

合理的开发流程：

| 步骤 | 动作 |
| --- | --- |
| 1 | 先用**纯 Prompt 跑通最小闭环** |
| 2 | **系统性分析 `prompt → response` 这条 pipeline 上的 bad cases** |
| 3 | 再用经典手法（**RAG、few-shot、CoT**）逐步逼近效果上限 |
| 4 | 一边做这个，一边**优化 Benchmark** |

两个容易被低估的判断：

1. **很多人低估了 Prompt 用 token 换精准度的潜力**——大模型能力越来越强，很多你以为很难的 case，其实只是 **prompt 没写好**；
2. 那怎么系统评估 prompt 是否还有优化空间？→ **Prompt 梯度测试**：同一批样本上逐步增强 prompt，看效果是否**持续提升**。

#### Prompt 梯度测试的迭代顺序

| 顺序 | 做什么 | 目的 |
| --- | --- | --- |
| 1 | 用最简单指令**横向对比多个基模**，pick 最合适的 | 先排除"模型选错"这个变量 |
| 2 | 根据**专家先验知识加 system prompt** | 对应上业务要求 |
| 3 | 拆一些 **workflow 来强化 PE**（比如手动/自动加上下文） | 让模型有参考信息 |

#### 什么时候该"换层"：Prompt 燃尽的判据

> 如果随着 Agent 里面流动的 prompt **逐步增强，效果仍然几乎不变**，说明对当前业务，**Agent 策略已经燃尽**，进入下一步 **LLM 策略**。

### 2.2 LLM 策略：把"说给模型听"变成"让模型学会"

先纠正一个误解：**LLM 策略不是为了替代 Agent 策略。**

| | Agent 阶段 | LLM 阶段 |
| --- | --- | --- |
| 手段 | 在 **Prompt / Context / Workflow** 里告诉模型**应该怎么做** | 让模型**自己学会**应该怎么做 |
| 收益 | 灵活、迭代快 | 减少每次都给 prompt 的成本，继续提高效果和稳定性 |
| 定位 | 已验证有效的**非参数化先验** | 把它训成模型的**参数化行为** |

> 做 Agent 开发过程中，如果遇到了**效果、稳定性、成本瓶颈**，就可以考虑进入 LLM 策略——把 Agent 策略已经验证有效的 **60 分方案**，做得**更稳定、更便宜、更 scalable**。

### 2.3 SFT：把稳定先验写进参数

SFT 的定位：**把 Agent 策略已经验证有效的先验，固化成模型稳定的行为模式。**

作者列了 Agent 开发阶段通常已经验证过的几类经验：

| 已验证的经验 | 典型的承载位置 |
| --- | --- |
| 某种**任务理解方式**有效 | Prompt |
| 某类 **few-shot** 能明显提升效果 | Prompt / Context |
| 某种 **Tool Routing** 更稳定 | Workflow |
| 某种**输出格式**更符合下游要求 | Prompt / 后处理 |
| 某种**拒答边界**更符合业务预期 | Prompt / 策略 |

这些东西**一开始都可以写在 Prompt 和 Workflow 里**；但如果它们**已经过 Benchmark 验证**、而且**高频、稳定、长期不会频繁变化**，就可以考虑通过 SFT 训进参数。

#### SFT 前最重要的问题 + 一条可操作的分界线

> **哪些 Agent 阶段学到的经验，真的值得被固化进模型？**

作者给的原则：

> **高频变化的信息继续留在 Context，长期稳定的行为才值得训进 model。**

| 类型 | 例子 | 该不该训进模型 |
| --- | --- | --- |
| 高频变化的信息 | 实时库存、活动规则、最新政策 | ❌ 即使很重要，也不适合 |
| 长期稳定的行为 | 固定输出习惯、稳定业务 SOP、Tool 调用方式、任务拆解范式 | ✅ 适合参数化 |

#### SFT 的难点是数据——而且难在"行为一致性"，不是"答案质量"

SFT 本质上就是告诉模型：**遇到这种情况，以后就应该这么做。**

所以最怕的是**行为分布自相矛盾**：

| 同一个业务场景里 | 模型学到的不是"灵活" |
| --- | --- |
| 一部分数据要求**拒答**，一部分要求**正常回答** | 而是**不确定性** |
| 一部分要求**严格 JSON**，一部分允许**自由文本** | 而是**不确定性** |
| 一部分要求**先调用工具**，一部分**直接凭模型知识回答** | 而是**不确定性** |

由此得出一个很有价值的视角转换：

> **SFT 的数据清洗，不是在清洗低质量答案，是在整理模型最终的行为分布。**

推论：
- **SFT 数据不是越多越好**，更重要的是**数据质量、行为一致性**；
- **未经 Benchmark 验证的 Prompt Hack，不能因为看起来有效就直接扩数据训进去**——否则只是把一个**还没想明白的策略永久写进参数**。

### 2.4 RL：把业务评价标准变成 Reward

作者用两个比喻区分 SFT 和 RL（原文的"抄版本答案"梗）：

> **SFT 是教模型抄版本答案拿到好结果**（codex、簿肌、自媒体、孙学、早 C 晚 A 护肤、低糖高蛋白饮食、伪素颜、雅思 7.0、拿实体黄金）；
> **RL 是放大好结果为大结果，让模型自己想办法拿到**（来读研 or 去实习）。

> 前面说 **SFT 难在数据质量，那么 RL 难在反馈信号**。

#### 为什么前面要花那么多时间做 Benchmark

> 因为**到了 RL 阶段，Benchmark 不只是测试，是反馈**。Rubric 定义什么叫好，Judge 判断好不好，这个判断**转化成 RL 阶段的 Reward，直接影响模型往哪个方向优化**。

#### RL 最危险的地方：reward 可能不是业务真正要优化的东西

风险的传递链：

```
Rubric 没对齐业务  →  Judge 没对齐人工（不稳定）  →  Reward 只是离线指标的近似
                                                          ↓
                                          模型"学好学坏都是学"
                                                          ↓
                              离线 Reward 涨了 ≠ 线上业务指标一定会涨
```

最后仍然回到 **Online Metric**（闭环收口）：

> 上线拿到新的**用户后验** → 更新 **Benchmark** → 拉 **bad case** → 修 **Rubric** → 调整**数据和 Reward** → 进入下一轮迭代。

### 2.5 三层分工一张表

| 层 | 做什么 | 输入 | 输出 |
| --- | --- | --- | --- |
| **Agent 阶段** | 积累**专家先验** | 业务知识、bad case | Prompt / Workflow / Rubric |
| **SFT** | 把**稳定先验写进参数** | 经过 Benchmark 验证的行为 | 模型参数里的稳定行为 |
| **RL** | 把**业务评价标准变成 Reward** | Rubric + Judge | 模型朝目标继续优化 |

> **reward 设计得好，模型会更稳定地朝业务目标优化；reward 设计错了，模型会更极致地学错。**

## 3. 写在最后：四个"有争议 maybe 有价值"的讨论

作者最后列了四组对立观点（原文没有下结论）：

| 争议点 | 一方 | 另一方 |
| --- | --- | --- |
| **过拟合** | 有过拟合的风险 | 只要**训练集 cover 业务场景**，过拟合**反而是我们的目标** |
| **灾难性遗忘** | 有灾难性遗忘的风险 | **遗忘是一种数据提纯** |
| **微调有没有必要** | 做 Agent 开发的朋友：**workflow 才是通往 AGI 的道路**，微调只是参数内卷、原地踏步 | （作者未给对立面，留给读者） |
| **效果上限归谁** | 做 AIGC 的朋友：真正决定应用**效果上限**的，始终是**模型自身的能力边界** | （同上） |

> 这四组的共同点：**争的都不是技术能不能做，而是"目标该定在哪一层"**。
> 结合正文看，作者自己的答案其实已经给出——**先验放在哪一层，取决于它的变化频率和验证状态**（见 2.3 表）。

## 4. 复习版结论

1. **开发 vs 算法**：0 → 60 是开发，60 → 80 并不断追高是算法；分水岭是**评价标准从"过程指标"换成"真实业务指标"**。
2. **总闭环**：**Benchmark → 策略 → 上线**。离线评测是"先验的近似"，上线后验再回来修先验。周期长、成本高是必须做离线 Benchmark 的原因。
3. **Rubric 是根**：把模糊业务目标翻译成"人 / LLM / 程序能稳定执行"的评价标准。**Rubric 之于评测 ≈ Harness 之于执行**（都是把模糊目标翻译成可执行物）。
4. **人标不一致先怪 Rubric**：人人一致率低，多半是 Rubric 不够清楚，要拆标准、补边界 case，而不是换 Judge。
5. **离线涨、线上不涨 → 先怀疑 Benchmark 没对齐业务**，而不是先调策略。
6. **评测四级 scaling**：Rubric（可描述）→ Human（可靠但不 scale）→ LLM Judge（自动化，但成本随规模线性涨）→ RM（规模化，但有 Reward Hacking，需定期校准）。
7. **策略先 Prompt**：纯 Prompt 跑通最小闭环 → 分析 bad case → RAG / few-shot / CoT 逼近上限 → 同步优化 Benchmark。用 **Prompt 梯度测试**判断是否燃尽。
8. **换层判据**：prompt 越加效果不变 → Agent 策略燃尽 → 进 LLM 策略；遇到效果/稳定性/成本瓶颈 → 把 60 分方案做稳、做便宜、做 scalable。
9. **SFT 判据**：**高频变化的留 Context，长期稳定的才训进参数**；难点是**行为一致性**（数据清洗 = 整理行为分布），不是答案质量，更不是数据量。
10. **RL 判据**：难在**反馈信号**；Benchmark 在 RL 阶段是**反馈**而非测试；Rubric/Judge 不对齐会让 reward 变成"离线指标的近似"，学坏也是学。

## 5. 落点：这篇对我们的用法（求职向）

> 以下是本笔记的整理视角，不是原文内容。

文章标题说的是"开发 → 算法"，而作者给的分水岭正好可以当**面试/简历的分层自检**：

| 自检问题 | 开发侧答法 | 算法侧答法 |
| --- | --- | --- |
| 你怎么知道效果变好了？ | "跑的 case 都通了" | "同一批样本上指标从 X 到 Y，且这批评测对齐了线上" |
| 效果不好怎么办？ | 改 prompt 再试 | 先归因到 **Rubric / Case / Judge / 策略** 哪一层，再动 |
| Prompt 优化到头了怎么走？ | —— | 判断"燃尽"后进入 SFT / RL，并说明哪些先验值得参数化 |
| 评测成本扛不住怎么办？ | —— | LLM Judge → 蒸馏 RM 的规模化路径 |
