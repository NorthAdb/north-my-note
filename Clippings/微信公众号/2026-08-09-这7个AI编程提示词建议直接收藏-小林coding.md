# 这 7 个 AI 编程提示词，建议直接收藏！

> **作者**：小林coding | **来源**：微信公众号 | **发布**：2026-08-09

---

## 💡 一句话总结

**提示词不需要写得很复杂。** 任务不同，最容易出错的地方也不同——针对 7 个高频场景（改代码前没摸清现状、小需求被写复杂、见错就猜、重构老代码、宣称开发完成、Code Review、输出太长），各配一条可直接粘贴的提示词。

## 📌 核心观点

- 很多人给 AI 的指令永远是一句「帮我处理一下」，结果：**小需求被写成大工程，Bug 还没复现就开始乱改，代码刚写完 AI 就拍胸脯说全部搞定**
- 每条提示词都针对一个**具体出错点**，而不是泛泛地要求「检查一下」
- 核心模式：**先理解 → 最小改动 → 用测试/证据说话 → 对抗性验证**

---

## 🗂️ 7 条提示词速查

### 1️⃣ 先摸清项目现状，再动手

**场景**：AI 拿到需求后，还没摸清项目现状就直接开始改代码。

> 「先不要修改代码。先阅读相关代码、测试、配置、依赖和相邻功能的实现，弄清楚项目当前的技术栈、代码约定和可以复用的逻辑。然后用自己的话复述需求，列出关键假设和最小改动方案。只有代码库里找不到答案，并且会影响方案选择的问题，才需要问我。等我确认后再动手。」

### 2️⃣ 最小改动，别过度设计

**场景**：小需求总被 AI 写得特别复杂。

> 「用最小改动实现。不要为未来需求增加抽象，不要处理实际不会发生的错误。先读相邻文件，匹配项目现有风格。」

### 3️⃣ 先复现，再修 Bug

**场景**：AI 一看到报错就开始猜答案。

> 「先不要修复。写出能稳定复现问题的最小测试，确认 Bug 真实存在后，再根据证据定位根因。」

### 4️⃣ 重构前，先补测试固定行为

**场景**：准备用 AI 重构老代码。

> 「先不要重构。先补一组测试，固定当前所有行为，包括奇怪的边界情况。测试必须在原代码上全部通过。」

> ⚠️ 这一步很重要。**连旧代码现在怎么工作都不知道，所谓重构，很可能只是换一种方式把它改坏。**

### 5️⃣ 对抗性测试，别只让 AI「检查一下」

**场景**：AI 说代码已经开发完成了。

> 「对刚才的代码做一次对抗性测试，重点攻击异常输入、边界值、并发、网络失败和错误假设。发现问题后修复，并补上永久回归测试。」

> 💡 相比让 AI 泛泛地「检查一下」，让它**真正写测试攻击代码**，结果会靠谱很多。

### 6️⃣ Code Review 聚焦实质问题

**场景**：让 AI 做 Code Review。

> 「审查最后一次提交，只检查安全、性能和逻辑问题，忽略代码风格。每个问题必须给出文件、行号和触发条件。」

> 💡 不加「忽略代码风格」，AI 很容易给你挑一堆命名和格式问题——看起来写了很多，真正有用的没几条。

### 7️⃣ 用 HTML 代替 Markdown 长文

**场景**：AI 输出的方案太长，根本看不下去。

> 「不要输出 Markdown。把结果做成一个单文件 HTML，用标签页、流程图和颜色展示重点，生成后直接在浏览器打开。」

> 💡 尤其是**架构方案、PR 解释和技术调研**，HTML 通常比几百行 Markdown 好读得多。

## 🎯 使用要点

1. **按场景选用**：遇到对应场景，直接丢给 Agent 就行
2. **核心模式**：理解 → 最小改动 → 证据驱动 → 对抗验证
3. 提示词里的原则可以**组合使用**（如：最小改动 + 先补测试）
4. 如果你 vibe coding 中也积累到好用的提示词，欢迎一起分享交流
