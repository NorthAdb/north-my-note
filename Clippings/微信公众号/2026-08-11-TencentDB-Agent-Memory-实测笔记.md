# 腾讯把 Agent 记忆系统开源了，TencentDB Agent Memory 实测！

> **来源**：Datawhale《腾讯把 Agent 记忆系统开源了，TencentDB Agent Memory 实测！》（作者：李秀奇，2026-08-03）

> **开源地址**：https://github.com/Tencent/TencentDB-Agent-Memory（1.1w+ ⭐）

> **一句话结论：Agent 需要的记忆能力，正在从应用层下沉到数据库层。** 记忆不是存起来就行，而是「写入 → 提炼 → 检索 → 更新」的完整链路，配合四层记忆金字塔、三条检索路径与冲突仲裁，才能让模型跨会话记住该记住的。

## 🎯 为什么需要 Agent 记忆系统

如果你正在用不带长期记忆的 AI 编程工具，这些场景一定不陌生：
- 你说过 PPT 用 HTML 写、别给 pptx，下次开新会话它照样给你 pptx；
- 你纠正过一次的毛病，它下次照犯；你提过的偏好，它下次清零。

本质都一样：**对话一结束，上下文就被销毁，模型没有任何跨会话的持久状态。**

## 一、从个人记忆到团队记忆

### Agent Memory 个人记忆的四个维度

一条记忆从产生到被用上，要经过 **写入、提炼、检索、更新** 四步。这四步在链路上前后依赖，前一步的输出就是后一步的输入——哪一步掉链子，结果都是这一轮拿不到该有的记忆。而且掉链子的方式往往不是报错，是**安静地返回空结果**。

写入、提炼、检索都走公开接口，整条链都可见：写进去什么、提炼成什么、召回了什么、各环节耗时多少。

![记忆生命周期：写入 → 提炼 → 检索 → 更新](https://gitee.com/cheng-jiaqing/images/raw/master/tencentdb-agent-memory-20260803-02.png)

### Memory Hub 把个人记忆推到团队层

腾讯云数据库 7 月发布的 Team Memory 版本把关注点拉到团队层面。多个 Agent、多个成员共用一套记忆时，知识怎么迁移、权限怎么划分、资产归谁所有，是另一组系统性问题。

官方方案是把四类资产汇入同一个池子：

| 资产类型 | 存什么 |
| --- | --- |
| **Skill** | 验证过的操作流程 |
| **Wiki** | 团队文档 |
| **CodeGraph** | 代码仓库知识 |
| **Chat Memory** | 历史交互 |

这四类资产经过审核和共享，再挂给新的 Agent，新 Agent 就能接着团队已有的进度往下做。

> **团队记忆不是个人记忆的放大版**：个人记忆错了自己纠正，团队记忆错了会被所有人继承；个人记忆没有权限边界，团队记忆里存着谁能看、谁能改、谁能删。

## 二、四层实测：从时效性到更新演化

### 第一层：实测时效性（写入多久能被查到）

写入分两层：
1. **落盘**：你的话说完，原文当场原样存进本地流水账，**毫秒级**完成——这一层保证"不丢"；
2. **提炼**：系统后台调一次模型，通读对话、分出场景、抽出重点、做成结构化卡片——这一层保证"能查"。

实测：写入"我习惯早上 6 点起床跑步，晚上 11 点前睡觉"，每 5 秒查一次。**第 5 秒还查不到，第 10 秒卡片出现**。后台日志显示提炼任务耗时约 6 秒。

![时效性测试截图](https://gitee.com/cheng-jiaqing/images/raw/master/tencentdb-agent-memory-20260803-04.png)

**结论**：从一句话到一条可检索的结构化记忆全程约 10 秒，自然聊天几乎无感。⚠️ 唯一要注意**批量场景**：写脚本载入历史对话时，空窗期得算进去，写完不能立刻查。

### 第二层：实测提炼质量（一口气说完 vs 分多次说）

设计两组对照（主题刻意不同，避免去重机制干扰）：
- **A 组**：一次性说完三条项目规范（pnpm 不用 npm、代码注释用中文、提交记录以中文动词开头）→ 提炼出 **1 张**卡片，三条全写入；
- **B 组**：分三轮说另外三条文档格式规范（避免第一人称、标题用陈述句、统一 Markdown 不用 Word）→ 提炼出 **2 张**卡片，共享同一场景名。

![提炼质量测试 A 组](https://gitee.com/cheng-jiaqing/images/raw/master/tencentdb-agent-memory-20260803-05.png)

![提炼质量测试 B 组](https://gitee.com/cheng-jiaqing/images/raw/master/tencentdb-agent-memory-20260803-06.png)

**结论**：一次说完倾向合成一张卡片；分多轮说按提炼批次拆成多张，但**仍落在同一场景下，检索时一起被召回**。两种说法的信息完整度没有差别——不必为了"让系统记得准"而刻意憋着一次说完。

### 第三层：实测检索命中（换个说法还认不认得）

先把"用户完全不能吃辣，对辣味食物有严格禁忌"存进记忆库，用八种不同说法查询：
- 带"辣"字的说法都能查到；
- **"川菜""忌口""spicy food"一条都召不回**。

原因：**语义召回默认是关着的**。打开语义召回后，系统会同时跑第二条路——把问题和卡片各自转成"语义指纹"（文字含义 → 数字坐标），按语义距离判断是否相关。

![检索命中测试截图](https://gitee.com/cheng-jiaqing/images/raw/master/tencentdb-agent-memory-20260803-07.png)

### 第四层：实测更新演化（旧偏好怎么处理）

写入四轮对话：①"项目数据库必须使用 PostgreSQL" ②③无关内容 ④"改用 MySQL"。

查库后发现**旧卡片和新卡片都还在**：旧卡片原封不动保留；新卡片明确记录"决定将数据库从 PostgreSQL 切换到 MySQL"，时间顺序和变更动因都被保留。

![更新演化测试截图](https://gitee.com/cheng-jiaqing/images/raw/master/tencentdb-agent-memory-20260803-08.png)

写新卡片前系统会做**冲突仲裁**：先在现有记忆里找出相似的候选卡片，再交给模型判断该**新增、跳过、覆盖还是合并**。这次语义召回没开，新旧两条记录字面几乎无重叠（只共享"数据库"三字），没能找到候选，新内容直接存成新的变更记录。后续 Agent 同时看到两张卡片，可从时间线判断哪条是现行偏好。

## 三、背后的核心机制设计

源码拆解共七块：**底座是四层分层（L0→L3），往上是写入、检索、注入三条主干，再加上冲突仲裁、短期记忆、故障降级三处兜底。**

### 记忆金字塔：L0 → L3 四层分层

为什么记忆不能直接存成一个列表？你想要证据完整就得存原话，想省 Token 就得压缩成摘要——**同一份数据没法既是原文又是摘要**。解法是拆成四层，从底到顶越来越精简：

| 层级 | 内容 | 特点 |
| --- | --- | --- |
| **L0 流水账** | 你和助手的原话，本地文件 + 数据库各一份 | 一字不改，不做任何提炼，留证据 |
| **L1 记忆卡片** | 后台通读对话：按情境分段 → 抽结构化事实 | 每张卡片只记一件事，类型只有偏好/事件/规则，带优先级 |
| **L2 场景档案** | 同一情境下的卡片打包成文件，按情境组织不按日期 | 文件头记创建/更新时间、摘要、热度值（被检索命中 +1） |
| **L3 人格摘要** | 从所有场景档案提炼的稳定画像——"这个用户是谁" | 四层里唯一不需要检索的，每次新会话**无条件注入**，必须够短够稳定 |

![记忆金字塔 L0 → L3](https://gitee.com/cheng-jiaqing/images/raw/master/tencentdb-agent-memory-20260803-09.png)

> **四层各管一段：L0 留证据，L1 保精度，L2 保情境，L3 保效率。** 底层存数据库全量可检索；高层写 Markdown，人能直接读、直接改。四层可串起来：人格摘要 → 场景档案 → 记忆卡片 → 原始对话，平时给高密度摘要，纠错时给完整证据链。

### 写入与提炼：分离式处理

写一条记忆只需一个动作：把这一轮的用户输入和助手回复交给系统，**原始对话毫秒级落盘**（只是录音，不做任何理解）。记忆卡片没有顺手一起做，因为**提炼绕不开模型**——"我不吃香菜"是长期偏好，"今天中午吃了火锅"是一次性事件，文本上没有任何区别，只有理解内容才能分开。

提炼是**后台异步**跑的（模型调用有成本有延迟，不能卡主流程）。触发条件：
- 每满 **5 轮**对话；或停止输入 **10 分钟**；或手动立即触发；
- 新会话开头有**预热**：前几轮阈值从 1 开始递增（1、2、4 轮），之后稳定到 5 轮。

每张卡片的类型和优先级由模型判断，没有写死规则——好处是灵活，代价是不可预测。

### 检索与注入：平衡精度和成本

三条检索路径：

| 路径 | 机制 | 特点 |
| --- | --- | --- |
| **字面匹配** | 全文索引 + 关键词稀有度打分，中文先分词再"或"匹配 | 快、省钱，但死板；卡片少时稀有度分数失真（有补救路径：放弃阈值过滤，直接信任索引排序） |
| **语义指纹** | 问题和卡片各自转成数字坐标，按语义距离匹配 | 换说法、跨语言都能召回；需额外配模型服务，**默认没开** |
| **混合检索** | 前两条路同时跑，排名叠加器合成榜单 | 只比名次不比原始分数（两套计分体系没有可比性） |

> ⚠️ **容易踩的坑**：策略默认值是混合检索，但语义能力默认关闭——**零配置装完实际跑的是纯关键词（字面匹配）**。要真正用上混合检索，得先配好语义服务。

**注入**：每轮对话开始前，把当前句和记忆库做一次匹配，召回最相关卡片，全程 **5 秒超时保护**（超时跳过注入）。召回内容分两处放置：
1. **用户消息前面**：本轮动态召回的记忆卡片，每轮都变；
2. **系统提示末尾**：人格摘要、场景导航、工具指南，几轮才变一次。

> 分开放是因为大模型服务商会**缓存系统提示**这段稳定前缀（命中缓存不重复计费）——把每轮都变的卡片塞进系统提示会让缓存立刻失效。

还有**预算控制**：单条记忆有长度上限，本轮注入有总字符上限；并在提示词里软约束 Agent 每轮主动检索不超过 3 次（软约束，非代码硬限流）。

### 冲突仲裁：解决记忆更新

「必须用 PostgreSQL」和「改用 MySQL」字面矛盾，但矛盾至少有三种可能：你改主意了（覆盖）、两个不同项目（并存）、你前后不一致（留两条给人判断）。**三种在文本上长得一模一样**，只能靠理解上下文区分，所以写一条记忆要多调一次模型。

仲裁分两阶段：
1. **候选召回（不调模型）**：新卡片转语义指纹，找距离最近的几张；语义不可用降级到关键词召回；两条都不可用跳过这一步；
2. **模型判断**：把新卡片和候选老卡片一起打包，一次问模型该新增、跳过、更新还是合并。

> **关键**：第二阶段的判断质量完全取决于第一阶段召回到了什么。模型只能在给它的候选里做判断——**没召回到的老卡片，在它眼里等于不存在**。

### 兜底设计：记忆系统坏了也不影响对话

原则：**故障容忍优先于功能完整**。
- **检索侧**：语义和关键词都可用跑混合；只有一条可用降级成那一条；两条都不可用返回空结果；
- **写入侧**：去重判断超时全部存为新卡片；语义指纹写入失败不影响已落盘的原始对话；召回超时跳过本轮注入。

**最坏情况是这一轮没有记忆可用，但对话还能继续。**

**单次任务太长**（如改跨十几个文件的 bug，几十轮上下文撑爆）也有解法：把详细过程转存到外部文件，上下文只留一张**任务地图**（节点 + 箭头呈现状态流转，每个节点标编号和下一步动作）。思路和长期记忆一样：平时给折叠视图，需要时再展开。

> **官方基准（WideSearch 长任务）**：Token 消耗从 **2.21 亿降到 8500 万**，通过率从 **33% 提升到 50%**。

## 写在最后：上手建议

**安装**：默认配置用本地 SQLite 存储，装完即用；想换自己的大模型做提炼和画像生成，只需填三项：模型访问凭证、服务地址、模型名称。

**三种接入方式**：装成 Agent 平台插件 / 通过统一网关调用 / 在自研项目里直接引用。

**一个配置值得先想清楚：要不要开语义召回**
- 只需要记住格式规范、工具偏好这类**说法固定**的东西 → 不用开；
- 需要理解**自然语言表达**的偏好 → 需要开。

**趋势洞察**：放在以前，向量化、相似度检索、结果重排序全是应用层任务，现在变成了安装时的一个选项。**Agent 需要的记忆能力，正在从应用层下沉到数据库层。** 数据库给人存了几十年数据，现在要开始给 AI 存记忆了。
