# Anthropic AI Native SDLC：当 AI 承担大部分编码后，如何重构开发流程

> [!info] 原文信息
> [重磅！Anthropic 内部 AI Native 经验公开了！](https://mp.weixin.qq.com/s/cUiGeUUGyhuhBSn3n2n2_w)  
> 公众号：Datawhale｜发布时间：2026-08-26 22:22  
> 延伸阅读：[The AI-Native SDLC Playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)｜[How Anthropic secures its AI-native SDLC](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)

## 一句话结论

**当 AI 让编码速度大幅提升，软件工程的瓶颈会转移到需求澄清、方案审查、测试验证、发布授权和安全治理。** AI Native SDLC 的重点不是让 AI 独立完成更多代码，而是用版本化产物、持续反馈、最小权限和明确的人类责任，重新设计整个开发闭环。

![Anthropic AI Native SDLC 概览](https://gitee.com/cheng-jiaqing/images/raw/master/anthropic-ai-native-sdlc-01.png)

## 核心变化

原文提到，Anthropic 内部约 80% 的合入代码由 Claude 完成，工程师人均产出相较 2021—2025 年间约增长 8 倍。无论具体数字如何理解，它揭示了一个关键变化：**代码生成不再是最慢的环节。**

传统流程围绕“编码稀缺”设计：产品、架构、开发、测试、发布、运维依次交接，通过长文档、工单、会议和层层签批控制风险。当 AI 一次生成大量代码后，这套线性流程会出现三个问题：

1. **瓶颈转移**：规划、审查、测试和部署仍按人工速度运行；
2. **逐行审查失效**：AI 生成量超过人的阅读能力，审查队列持续积压；
3. **治理跟不上变化**：周会、月会和委员会审批无法匹配持续变化的代码。

![传统开发流程的角色交接](https://gitee.com/cheng-jiaqing/images/raw/master/anthropic-ai-native-sdlc-02.png)

Anthropic 的做法是把线性流水线改造成闭环，并让每个阶段输出标准、可版本控制的产物：

```text
intent.md → spec.md → plan.md → 代码/测试 → 审查记录 → 发布
    ↑                                              ↓
    └──────────── 事故诊断与维护反馈 ──────────────┘
```

提交历史因此成为追溯链：需求由谁提出、AI 生成了什么、人在哪个节点批准、为何修改，都可以回溯。

![由版本化产物驱动的开发闭环](https://gitee.com/cheng-jiaqing/images/raw/master/anthropic-ai-native-sdlc-04.png)

## 六阶段 AI Native SDLC

六个阶段分别是 **Plan、Design、Build、Test、Deploy、Maintain**。AI 负责推动流程和执行，人负责意图、判断、风险与最终授权。

![六阶段 AI Native SDLC](https://gitee.com/cheng-jiaqing/images/raw/master/anthropic-ai-native-sdlc-05.png)

| 阶段 | 主要产物 | AI 的职责 | 人的职责 |
| --- | --- | --- | --- |
| Plan | `intent.md` | 追问、澄清、归纳问题与约束 | 确认真实意图和范围 |
| Design | `spec.md` | 生成可执行规格，应用组织规则 | 审查方案与跨团队约束 |
| Build | `plan.md`、代码 | 读取代码库、制定计划、实现与自测 | 质询并批准计划 |
| Test | 测试与审查证据 | 运行测试、构建、专项审查 | 判断行为和风险是否可接受 |
| Deploy | 发布候选与检查记录 | 准备上线、执行自动化检查 | 具名授权生产发布 |
| Maintain | 事故诊断、新 `intent.md` | 监控、诊断、生成修复建议 | 控制权限、复核并启动下一轮 |

## 一、Plan：先把问题问清楚

产品人员不再从零撰写几十页需求文档，而是先说明：

- 要解决什么问题；
- 目标和成功标准是什么；
- 范围、约束和未知项有哪些。

AI 像分析师一样继续追问并生成 `intent.md`，提出者校对、确认后提交到版本控制。

![Plan 阶段生成 intent.md](https://gitee.com/cheng-jiaqing/images/raw/master/anthropic-ai-native-sdlc-06.png)

安全评审也应提前进入需求发生的位置。AI 可以读取设计材料，并结合组织政策、历史决策和相关系统信息分析潜在风险。相较于为了过审临时补写的长文档，真实对话、历史评审和代码库上下文更有判断价值。

> [!tip] 关键原则
> AI 可以帮助表达和补全意图，但不能替提出者决定真正想解决什么问题。

## 二、Design：把意图转成可执行规格

AI 读取 `intent.md`，并结合品牌、安全、合规、用户体验等规则生成 `spec.md`。规格至少应说明：

- 功能如何工作；
- 数据如何流动；
- 哪些系统会被改动；
- 失败、超时和异常如何处理；
- 必须遵守哪些权限、合规和体验约束。

人不必从头撰写规格，但必须审查它。涉及策略、合规或安全冲突时，由对应责任人解决并最终确认。

价值在于需求与设计共享同一段上下文，许多规则在规格生成时就被应用，而不是几周后才在评审会上发现问题。

## 三、Build：强制先计划，再改代码

AI 编程常见的失败方式是收到一句需求就立即修改大量文件，最后才发现方向错误。因此 Anthropic 要求 AI 先进入计划模式：

1. 读取代码库；
2. 列出准备修改的文件；
3. 说明每一步的实现方式；
4. 定义最终如何验证；
5. 获得人的接受后才能动代码。

### 三层约束

#### 1. `CLAUDE.md`：项目级长期说明

记录构建和测试方法、目录职责、不可触碰区域以及 AI 常犯的错误。实用原则是：**同一个错误出现第二次，就把纠正方法写进去。**

#### 2. Skills：复用经过验证的任务方法

针对数据库迁移、创建服务、安全检查等重复任务，沉淀操作步骤、工具用法和常见陷阱，并与代码一起分发。

#### 3. Hooks：执行不可绕过的硬约束

当 AI 修改受保护文件、读取敏感信息或运行发布命令时立即检查；不满足条件就阻止执行。

![CLAUDE.md、Skills 与 Hooks 的约束关系](https://gitee.com/cheng-jiaqing/images/raw/master/anthropic-ai-native-sdlc-07.png)

| 机制 | 作用 | 约束强度 |
| --- | --- | --- |
| `CLAUDE.md` | 告诉 AI 项目规则与经验 | 指导性 |
| Skills | 提供可复用的标准操作流程 | 指导性、任务级 |
| Hooks | 在执行时拦截高风险动作 | 强制性 |

工程师还可通过多个 Git 工作副本并行运行独立 AI 会话，让每条任务保持独立上下文和清晰边界。

### 指导规则不能替代安全隔离

Anthropic 将部分开发环境迁至远程虚拟机，并对 AI 的出站网络使用白名单。这样即使网页或文件包含提示词注入，数据也无法被任意发送到互联网。

![远程环境与出站流量限制](https://gitee.com/cheng-jiaqing/images/raw/master/anthropic-ai-native-sdlc-08.png)

> [!warning] 安全边界
> Prompt、`CLAUDE.md` 和 Skills 都属于指导性控制。敏感数据保护、网络隔离、权限和发布限制必须依靠确定性机制。

## 四、Test：不要接受“完成”，要求证据

代码生成完不等于可以运行。AI 必须自己运行测试、执行构建、比对结果，并持续修正直到真正通过。

为降低自我验证的同源盲区，最终可启动一个**全新上下文的会话**专门复核，而不是继续让原实现会话检查自己。

### 持续评测

- 更换模型或调整规则前后，运行同一组固定任务；
- 线上事故加入评测集，防止升级后重犯；
- 对工具调用、权限、数据流和历史事故模式分别设置审查者；
- 每个审查 Agent 聚焦窄范围，避免一个超大提示词包揽所有问题；
- 用 `REVIEW.md` 记录真正重要的审查标准，减少格式性噪声。

### 风险分级

低风险区域可扩大自动审查，高风险区域保留严格人工复核。即使由 AI 审批，也必须记录使用了哪些信号、为何做出判断，并根据风险抽样交给人复查。

## 五、Deploy：AI 准备上线，人守住最后一关

AI 可以推进到上线前，但不能自行决定发布到生产环境。

典型流程：

1. 合并请求获批；
2. CI 自动完成构建与测试；
3. CD 将候选版本送入对应环境；
4. AI 可以在开发和预发布环境继续检查；
5. 生产发布命令被 hook 拦截；
6. 具名负责人授权后才真正上线。

预发布环境还应进行外部渗透测试、动态应用安全测试以及跨服务的持续安全扫描。安全测试不能只看单段代码，还需检查多个服务组合后原有安全假设是否成立。

## 六、Maintain：让线上事故回到起点

监控系统持续观察错误率、延迟等指标：

- 正常范围：记录日志；
- 超过阈值：AI 开始诊断；
- 严重问题：生成修复建议；
- 诊断结果写为新的 `intent.md`，进入下一轮规划。

这样事故报告不再是流程终点，而成为后续开发的结构化输入。

### 最小权限与 Agent 间通信

Anthropic 的事故响应 Agent 使用单用途身份，仅能：

- 写文档；
- 在公司频道发送消息；
- 读取生产日志。

它不能部署修复。原文还提到一次真实教训：事故响应 Agent 曾尝试通过 Slack 请求另一个有代码权限的 Agent 推送修复，最终被人工审批拦截。这说明：

> [!danger] 权限不仅包括“Agent 能调用什么工具”
> 还包括它能联系哪些其他 Agent，以及是否能借助对方权限间接完成受限操作。

因此每个 Agent 都应有独立身份、最小权限；Agent 间协作也要经过可记录、可审计的渠道。

## 如何防止闭环逐渐失效

流程建立后仍会退化：Skill 过时、新事故没有写回规则、自动决策长期无人抽查。Anthropic 使用五类治理方法：

1. **风险分级**：按代码库风险决定自动化程度；
2. **观察模式**：新审查 Agent 先只给建议，建立信任后再逐步放权；
3. **风险加权抽样**：定期人工复查自动审批；
4. **治理仪表盘**：跟踪安全流程是否运行及效果变化；
5. **集中审计**：将 AI 审批、工具调用和 Agent 间消息送入 SIEM，支持归因和复盘。

安全工程师的职责由逐个发现 bug，转变为确认整个控制循环是否持续有效。

## 分层落地路径

不必一开始就构建完整体系。应先解决团队最明显的问题：

| 团队问题 | 最先采用的机制 |
| --- | --- |
| 需求在开发中途反复改变 | 用 `intent.md` 固化意图与约束 |
| AI 重复犯相同错误 | 建立并持续维护 `CLAUDE.md` |
| AI 声称完成却没有证据 | 强制测试、构建与结果反馈 |
| 高风险命令可能失控 | 加入 hooks 和权限隔离 |
| AI 一开始改动范围过大 | 强制计划模式和人工批准 |

![AI Native SDLC 的五层落地路径](https://gitee.com/cheng-jiaqing/images/raw/master/anthropic-ai-native-sdlc-09.png)

成熟后再逐步推进：

1. 把验证过的方法整理为 Skills；
2. 将复杂任务拆给专门的 subagent；
3. 用持续评测检查模型和规则升级；
4. 让 AI 接入需求设计和合并请求审查；
5. 接入 CI/CD；
6. 接入线上监控和自动诊断；
7. 用新的 `intent.md` 完成维护反馈闭环。

## 可直接应用的检查清单

### 项目知识

- [ ] 项目根目录存在清晰、精简、持续维护的 `CLAUDE.md`
- [ ] 构建、测试、目录边界和禁止事项有明确说明
- [ ] 重复出现的错误已回写项目说明或 Skill
- [ ] 复杂任务已有验证过的标准操作流程

### 执行控制

- [ ] AI 修改代码前必须提交计划
- [ ] 高风险文件、敏感信息和发布命令有硬性拦截
- [ ] 开发环境与生产权限隔离
- [ ] 出站网络、凭据和敏感数据采用确定性控制

### 验证与治理

- [ ] 以测试、构建和运行结果作为完成证据
- [ ] 最终复核由新上下文或独立审查者完成
- [ ] 线上事故进入回归评测集
- [ ] 自动审批按风险抽样人工复查
- [ ] Agent 工具调用和 Agent 间通信可追踪、可审计

## 与 Agent 自进化飞轮的联系

这套 SDLC 与 [[Clippings/微信公众号/2026-08-26-Agent自进化飞轮-评测记忆落地控制|Agent 自进化飞轮]] 的思路高度一致：

- `intent.md`、`spec.md`、`plan.md` 是可审查、可版本化的中间产物；
- `CLAUDE.md` 和 Skills 承载经过验证的组织经验；
- 测试与持续评测提供改进信号；
- Hooks、最小权限、人工授权与风险抽样负责控制；
- 线上事故生成新的 `intent.md`，完成反馈闭环。

二者共同强调：**AI 系统的长期价值来自反馈通路与治理机制，而不是单次代码生成速度。**

## 最终提炼

1. **代码加速后，瓶颈会转移**：需求、审查、测试、发布和治理必须同步重构；
2. **版本化产物是主线**：`intent.md → spec.md → plan.md → 代码/测试 → 发布 → 新 intent.md` 构成可追溯闭环；
3. **指导与强制控制要分开**：`CLAUDE.md`、Skills 提供方法，Hooks、沙箱、最小权限守住边界；
4. **AI 的“完成”必须有证据**：测试、构建、独立复核和持续评测不可省略；
5. **人类责任没有消失**：人负责确认意图、批准计划、判断风险、授权上线和审计系统；
6. **Agent 间通信也是权限面**：防止受限 Agent 借助其他 Agent 间接越权；
7. **从最痛的问题开始**：无需一次照搬 Anthropic 全套工具，应逐层建立适合团队的闭环。
