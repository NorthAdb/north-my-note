# 云端 Agent 架构：Harness 放沙箱还是放服务

> [!abstract] 一句话
> 两篇小红书帖子问的其实是同一个问题的两面：把 Agent 从「本地 CLI」搬进「云端 B/S 系统」时，**真正难的不是 agent loop，而是有状态的那部分**（会话状态、文件系统、沙箱生命周期）；而「harness 放沙箱里还是放服务里」，本质就是**把这份状态托管给谁**。

> [!info] 两帖是怎么凑到一起的
> - **帖一**（Bug🔗Life，09-01）：从**应用侧**提问——pi sdk 做大型 B/S 系统「怎么老是横向扩展很难呢，还是大部分是 agent sdk 都要自己做横向扩展呢？」
> - **帖二**（0xD800，09-04）：从**架构侧**提问——「云端 Agent：方案一 harness in sandbox，方案二 harness in service，你怎么选？」
> - 关键人物是重叠的：**0xD800** 在帖一里给出了全场最实操的「S3 + 无状态沙箱」方案，三天后自己开了帖二继续追问；**BoAI** 也在两帖都出现。
> - 所以这篇把两帖合成一条线：**帖一 = 问题（横扩难）→ 帖二 = 解法之争（harness 放哪）**。

# 一、帖一：pi sdk 做 B/S 系统，为什么横向扩展这么难

![pi sdk 封面：pi sdk 好像确实不太适合做大型的 B/S web 系统啊，怎么老是〔根据〕横向扩展很难呢，还是大部分是 agent sdk 都要自己做横向扩展呢](https://gitee.com/cheng-jiaqing/images/raw/master/cordis/2026-09-01-pi-sdk-封面.webp)

> 正文栏只有标签，问题写在封面图上。封面原文：「pi sdk 好像确实不太适合做大型的 B/S web 系统啊，怎么老是〔根据〕横向扩展很难呢，还是大部分是 agent sdk 都要自己做横向扩展呢」（"根据"疑为"感觉"的笔误）。

## 1.1 作者的真实约束（散落在评论区里，比正文更重要）

作者在跟评里陆续补全了场景，这几条决定了后面所有方案的取舍：

1. **要内嵌到应用里**，讨论的是 **sdk 不是 pi coding agent 产品**（有人拿 cline 来比，被作者直接纠正）；
2. **要求内网部署**，可能没有 serverless 基础设施（"需要自己上一套 openFaaS？"）；
3. **session 记录存在 jsonl 里**，SDK 也从 jsonl 恢复会话记录；
4. **单会话要处理 200MB 上传资料**；
5. **领导要 B/S 架构**，作者自己其实倾向 **local first**（"唉"）；
6. 具体痛点：**pi 的资源加载和用户 session 都挂在某个节点的文件系统上，这个节点挂了怎么办？**——高可用、高并发难搞。

## 1.2 评论区六条主线

### 主线 A：状态外置 + 无状态沙箱（0xD800，46 收藏，全场最实操）

> **0xD800**：我的 agent 文件直接进 s3，每次执行命令后全部 sync-back，沙箱有存活时间，长时间不操作就释放，以后复活再把文件写进去。

作者追问"是不是一个 session 对应一个沙箱"，0xD800 给出了完整流程：

> **0xD800**：我的文件元信息是存在**关系型数据库**的，初始化沙箱的时候，先把这个 session 的文件列表查出来，然后**从 s3 复制到沙箱目录**，然后启动沙箱。是的一个沙箱一个 session 会话，这种设计是针对**无状态沙箱**设计的。

关于会话记录的存储分层，他说得更细：

> **0xD800**：我是把会话历史归档为 **jsonl** 存到 s3；**元数据**还是存关系型数据库；归档的 **jsonl.gz 是保存 llm 请求记录用于排查问题**。

并且明确提醒作者**不要照抄本地 SDK 的假设**：

> **0xD800**：这种 sdk 针对本地客户端的吧，我觉得对于**服务端 agent 来说不能完全照抄**。

作者最后的收口（也是这帖的结论）：

> **Bug🔗Life**：发这个帖子就是初衷想问这个，总感觉这类 sdk 用到服务端好怪异啊，不过就算它怪，不用 nfsv4，用你的方案用 s3 和沙箱感觉**也可以完美解决**。

> [!note] 关于性能质疑
> **bobo**：「冷启动 + 文件复制。这性能不敢想。」
> **astonycat**：「sandbox 启动挺快，主要是文件复制吧。」
> **0xD800**：「80% 都不是冷启动的，那些无状态沙箱不也是这么干吗？……agent 这点性能跟 llm thinking 相比就是一下子的事情。」

### 主线 B：harness in sandbox + scaling sandbox（BoAI，11 赞，全场最高）

> **BoAI**：一般的方案就是 **harness in sandbox，然后 scaling sandbox**。也有 harness 做成 **serverless** 的方案，比如说 **claude managed agents**。如果想用 pi 做 serverless harness，可以看看我的项目 **openma-ai/open-managed-agents**，最近在做 pi 的方案。

作者顾虑内网部署，BoAI 的答复是：

> **BoAI**：一般的**无状态微服务也可以的，支持 node 部署**。

后续两人把话题延伸到"agent as a service"：

- **小红薯68F2D6A4**：团队在选"完整功能（如 AgentScope）"还是"轻量底座二开（如 pi）"上有分歧。
- **BoAI**：AgentScope 和 pi sdk 的封装粒度感觉差不多了。
- **Bug🔗Life**：AgentScope service 就像 Claude managed agents，也有点像你的 openma。
- **Bug🔗Life**：**OpenAI 也发布了 agent as service，就是下一波产品形态**；BoAI：昨天适配了哈哈。

> [!tip] 交叉验证
> `openma-ai/open-managed-agents` 实际存在：**276 stars · Apache 2.0**，描述为 *"Self-host AI agents with Claude Managed Agents and OpenAI Agents API support. Sessions, tools, subagents and recovery on your infrastructure."*，最近更新 2026-09-13——和评论时间线对得上。

### 主线 C：沙箱粒度之争 —— 一个 session 一个沙箱 vs 一个项目一个沙箱（帖一最长的一串）

这是全帖信息密度最高的一段，两方都讲了实话：

| 立场 | 谁 | 论据 |
|---|---|---|
| 一个 session 一个沙箱 | **0xD800** | 无状态设计：启动时把文件复制进去，变更同步出来；默认**保活 15 分钟**，无操作就释放，下次冷启动重新导入；**每个用户最多 3 个同时启用** |
| 一个项目一个沙箱 | **momo** | "用户 + 项目 + session，**一个项目一个沙箱容器**，容器资源做限制，用户可申请扩大，资源消耗小很多" |

momo 的反驳点很具体，值得记住：

> **momo**：**一个 session 一个容器上限太低了，宿主机很容易撑爆**，除非你对活跃的 session 做数量限制。
> **momo**：一个用户启动 10 个 session，一百个用户同时在线，就得**一千个容器**，资源太浪费了。
> **momo**：正常用户使用场景 **session 切换比项目会多很多**，一个用户创建一千个项目、同时在跑的概率很低。
> **momo**：沙箱也得是无状态的——沙箱启动后把项目信息拷进去，session 全关就销毁，**主要是减少沙箱容器的创建**。

0xD800 的回应则是"先看规模"：

> **0xD800**：没在用的 Session 会自动销毁的……如果真有那么多用户用这个产品，那么显而易见**必须加配置**了。
> **0xD800**：目前单实例开发的，分布式就是多部署几何个服务就好了。〔原文如此〕
> **0xD800**：状态是 redis/MySQL 管理的。

> [!warning] 这段争论的实质
> 不是"谁对"，而是**沙箱复用粒度 = 成本模型**：session 级 = 隔离最干净、容器数最多；项目级 = 复用率高、但要处理并发与资源配额。选哪个取决于"用户活跃 session 数 / 项目数"的真实分布。

### 主线 D：概念之争 —— "横向"到底指什么 & SDK 是不是"太简陋"

> **老豆子 脾气大**（4 赞）：现在 AI SDK 都是**最小功能原则**，保证单 agent 独立运行、上下文优化吧，你说的横向应该是**功能性扩展 / 多 agent 扩展**？
> **Bug🔗Life**：功能性属于纵向吧，**多 agent 算是横向**。

老豆子后面把结论说透了：

> **老豆子 脾气大**：这些 SDK 都是**基于本地策略进行恢复**的，如果执行过程中挂了，可选的是重启这个容器、找其他节点重新执行；**高可用场景要把过程内容魔改写到其他地方用来恢复，这改动不小**。
> **老豆子 脾气大**：现在考虑最多的就是**本机异常可恢复**……持久化不是大问题，可魔改的。
> **老豆子 脾气大**：这大文件（200MB）就更不适合云端处理了。

另一条支线是"pi 太简陋"：

- **顾青山**：我觉得它太简陋了，我选择 cline。
- **Bug🔗Life**：我要内嵌应用，讨论的是 sdk 不是 pi coding agent。
- **顾青山**：巧了，我说的就是 sdk。
- **Bug🔗Life**：那是我孤陋寡闻了，不知道 cline 还有 sdk。
- **momo**：pi 的 sdk 就是 coding agent，他的上层是 tui；**今天吃点什么哪**：pi core。

### 主线 E：托管 / serverless 路线与替代品

- **momo**：确实不适合多用户云场景，可以考虑 **vercel / cloudflare 的一站式 agent 方案**（跑在 serverless 上天然具备扩展性）。
- **momo**（另一位，落地自述）：**底座用 pi 做多租户 SaaS**，用户元信息用关系型数据库，**会话用 SSO**，**工作空间挂到一个沙箱容器**中——和 0xD800 的思路同构。
- **momo**：openai agents sdk 呢，只用 loop，不用 sandbox。
- **六个彩虹运动员灰烬**：mastra。

### 主线 F：本贴共识与未解

**已形成共识**

1. 难点在**会话状态 + 文件系统 + 沙箱生命周期**，不在 agent 逻辑本身；
2. 通行做法是**状态外置**（S3 / 对象存储 + 关系库 / SSO 会话）+ **无状态沙箱**；
3. **agent SDK 普遍只提供最小内核**（loop + 工具调用），横向扩展是上层应用自己要搭的；
4. 云端场景**不能照抄本地 CLI 的恢复策略**，要么改造成"过程状态可迁移"，要么换架构。

**没解决**

- 200MB/会话的大文件 + 单会话长任务是硬约束，评论区直接建议"**local first**"；
- "过程状态写到外部"具体怎么改、改动量多大，没人给出成体系的做法。

# 二、帖二：云端 Agent 架构 —— harness in sandbox vs harness in service

![云端Agent的架构讨论 封面卡片：方案一 harness in sandbox；方案二 harness in service](https://gitee.com/cheng-jiaqing/images/raw/master/cordis/2026-09-04-云端Agent架构讨论-封面.webp)

**封面卡片原文**

> 云端Agent的架构讨论。
> **方案一：harness in sandbox**
> **方案二：harness in service**
> 方案一是在**沙箱里面安装成熟 harness**。
> 方案二是在**服务里面跑 react loop 循环**。
> 方案二**更好掌控 agent 运行过程的状态**。方案一**做云端 coding agent 更好**。

**正文（作者自述背景）**

> 说下背景，我第一次接触云端 Agent 是在 Claude.ai 网页版，那时候国产 ai 的 chat 产品还停留在 rag 第一阶段（如首次消息搜索网络，纯聊天，没有工具调用能力）。此时的 Claude/manus 都已把云端 Agent 做得非常好了，agentic rag 用起来那是真爽，非常智能的感觉。
> Harness in Sandbox 这个方案我没有考虑过，我不太清楚什么场景会这么设计。欢迎交流。
> 我有一个云端 agent 开源项目：**L1yp/agentic-rag-platform**。

**作者自己补的方案二实现（评论）**

> **0xD800**：我把 agent 的 **react loop 放到服务里，状态放 redis/mysql**。agent 服务可横向扩展。体验地址：`https://agent.l1yp.com/`，可以多端实时同步最新运行进度。

## 2.1 支持方案一（harness in sandbox）的论据

> **BoAI**（3 赞）：**claude code 的云端版本就是 harness in sandbox**。我觉得就是因为随着 coding 任务越来越长，**sandbox 的存续期也越来越长**（可以理解为 sandbox 的存续期变得和 agent 的存续期一样长。而之前 claude.ai 网页端的 sandbox 生命周期只是很短的函数执行，或者像 ipynb 那样的简单状态维护），那还不如把 harness 放到 sandbox 里，**省得维护两个状态**。

> **笨笨的 clumsy**：in sandbox 可以**利用现成的 harness 工具，不用自己开发**。（作者补充：不过现成 harness 的状态数据要适配下。）

> **hh0104**：有的大厂用**第三方，Codex 这些，直接在沙箱装 cli，后端变成网关**，路由、转发请求这些。
> **hh0104**（更完整的一段）：沙箱跑 agent 的话，**后端就是个网关**——转发消息、统一协议、消息队列，要处理**时序、沙箱预热、实时性、会话管理**等一大堆问题；好处是 **harness 不用自己搭**，直接以镜像形式在沙箱里装 agent cli 就好，而且**扩展性好，只需要统一协议**，而且**用户身份问题好解决**。

> **Octavarium**（2 赞）：harness in sandbox **比较好落地，而且也好切 harness**，如果做 multiagent 甚至可以做不同 agent 的编排；但是对**状态管理、基建、时序、稳定性**等好多维度都是很大的挑战。harness in service 就是绑定一套 harness，**扩展性差点，但方案简单点，没有很复杂的分布式问题**。

> **冥想思者**：推荐是 **harness ➕ 沙箱**，注意 ➕ 这个词。——一条容易被忽略的折中：不是 in，是 和。

> **记录生活的卡尔**：可以看看**腾讯云开源的 CubeSandbox** 这个项目，**起一个沙箱 60+ms**，其实就可以做到每次调用 agent 的时候就将 agent 注入到沙箱当中，设置一个沙箱存活时间，一段时间不调用后就自动销毁，也比较省资源。

## 2.2 支持方案二（harness in service）的论据

> **0xD800**（作者）：我觉得 **harness in sandbox 的设计是不科学的**。

> **执剑**（2 赞）：**方案 1 不 scale**，没有分离环境和 agentic loop，对状态存储也不友好。**目前主流都是方案 2**，反驳请带例子。

> **AttachNowhere**：都不用，**沙箱里放个 daemon 执行操作，agent loop 跑在服务器进程里**。
> → 作者："那不方案 2 吗？" → AttachNowhere："看错了，是方案 2。"（这段乌龙恰好说明：很多"第三种方案"其实是方案二的变体）

> **富士摄momo**：harness in service **更加要处理断点重跑、记录每一轮状态**。——这是方案二被低估的成本。

## 2.3 第三条路 / 折中路线

> **沉睡的酱肘子**（6 赞，帖二最高赞）：sandbox 原先是适合**短生命周期**的，作为 agent **旁路工具**；但如果要跑 sandbox 内置 agent，**sandbox 和 agent daemon 的生命周期就需要捆绑在一起**，你就需要在**一个 linux 里闭环搭建所有 harness**。
> ↳ 他还补了一句价值观判断：**大部分能爆火的开源软件产品都是 local first**，你想想为啥，**简单即是健壮**。

> **dearmr6**：可以参考很多 IDE，就是**写脚本类的高危动作放沙箱，普通的技能工具调用还是本地**。我自己是这么做的，我们也是 SaaS 化的服务；还有一种就是 harness in sandbox，我们隔壁组是这么用的。

> **美少年**（2 赞）：沙箱现在主流的就两种场景——**第一种是 agent inside**，主要是云主机场景，做**常驻型任务**；**第二种是 agent outside**，比如 **RL 这种 job 场景**，做**即拉即消**的任务。**不同的场景需要不同的 agent infra**。

> **影子个人成长**：现在用的**沙箱当调用工具**。agent 服务是同一个，每个人有自己的沙箱，个人沙箱一段时间没有就销毁。

> **全网第一个讲 AI Infra**：一种是把 harness 放在沙箱里，一种是**把沙箱当一个调用工具**。

> **笨笨的 clumsy**（帖二里最有洞察的一条）：这会带来第二个取舍——**信源在下还是信源在上**。
> - **信源在下**：上层只是展示，比较简单，但是**做不了多副本高可用**；
> - **信源在上**：有些 harness 不原生支持需要 hack，而且自己管理上下文**基本等同于重新写一个**了。

## 2.4 infra 与成本的现实

| 评论 | 要点 |
|---|---|
| **中本喵** | **full E2B 成本太高**；**k8s + Kata 需要自己搭和维护** |
| **momo** | 腾讯开源了支持，就是**硬件适配麻烦** |
| **傅o_O** | harness in sandbox **成本比较高**，对 sandbox 要求高：**生命周期、快照恢复**这些 |
| **Dagugugugu** | 就自己做一套 E2B 呗，**难点不在 agent 侧而在于 infra** |
| **momo** | **agent in sandbox 就是为了省事，除了省事就没有优点了，给 infra 压力挺大**（作者回："我也是这么觉得的"） |

## 2.5 安全与身份

- **记录生活的卡尔**：第一种会更安全，如果 agent 有什么高危操作也只会影响沙箱吧。

# 三、把两帖合起来看：一张自检表

两帖的提问角度不同，但落到决策上收敛到同一组变量：

| 决策点 | 选 A：harness in service | 选 B：harness in sandbox | 依据（来自两帖） |
|---|---|---|---|
| **agent loop 在哪** | 服务进程里跑 react loop | 沙箱镜像里装成熟 harness | 帖二封面定义 |
| **状态放哪** | Redis/MySQL + S3（jsonl 归档）；信源在服务侧 | 沙箱本地文件 + 定期 sync-back 到 S3；信源在沙箱侧 | 0xD800 / 笨笨的clumsy"信源在上/在下" |
| **横向扩展靠什么** | 无状态服务多副本（天然可扩） | **scaling sandbox**（扩沙箱实例） | BoAI：harness in sandbox + scaling sandbox |
| **沙箱粒度** | 沙箱当工具，**session 级**、用完即销 | 沙箱即运行体，**生命周期与 agent daemon 绑定** | momo vs 0xD800 的沙箱粒度之争 |
| **主要代价** | 断点重跑、每轮状态记录、自己搭 harness | 状态管理 / 基建 / 时序 / 稳定性 + infra 成本 + 身份方案 | 富士摄momo、Octavarium、hh0104 |
| **适合谁** | 要**掌控运行过程状态**、多租户、需要自己做定制的场景 | **云端 coding agent**、任务越来越长、想复用现成 harness | 帖二作者结论；BoAI |
| **省事程度** | 要自己搭 | 装现成 CLI 就行，"除了省事没优点" | 笨笨的clumsy / momo |

> [!important] 三条可以带走的结论
> 1. **"云端 Agent 难"= 有状态的部分难**。两帖里所有跑通的人（0xD800、momo、hh0104）都在做同一件事：**把状态从"节点本地"搬到对象存储 / 关系库**，让计算（沙箱或服务实例）变成可回收的。
> 2. **粒度就是成本**。session 级沙箱隔离干净但容器数爆炸（momo：100 用户 × 10 session = 1000 容器）；项目级沙箱省资源但要管并发与配额。没有免费选项。
> 3. **折中路线正在变成默认答案**：**harness ➕ 沙箱**（旁路高危动作进沙箱，harness 留在服务里），或者按 **agent inside / agent outside** 分场景选 infra。

# 四、对我的启发 / 待验证

**启发**

1. 帖一那位作者的处境很典型：**领导要 B/S，架构却想 local first**。如果目标是"把本地 SDK 塞进云端"，真正的工作量不在 agent 逻辑，而在"会话 / 文件系统 / 沙箱生命周期"这一层——这句话可以当作评估任何"上云"方案的第一检查项。
2. **"信源在上还是在下"**这个提法很好用，比"有状态/无状态"更具体：它直接对应"能不能多副本高可用"这个硬指标。
3. 帖二作者的方案二实现（**react loop 在服务、状态在 redis/mysql、服务可横扩**）配上帖一的**沙箱无状态 + S3 sync-back**，其实就是一条完整可落地的路线：**loop 在服务、状态在外部、沙箱只是执行工具**。
